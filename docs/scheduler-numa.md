# NUMA Instance Types Design

Design notes for new families of instance types whose size is not fixed in configuration, but derived from the
NUMA topology of the Proxmox hosts: a VM that takes a whole NUMA node (`n1`), an aligned half of it (`n2`), or an
aligned quarter (`n4`).

Status: proposed.

## 1. Problem

Every instance type today is static: a fixed CPU/memory pair, either generated by `InstanceTypeOptions.Generate`
(`pkg/providers/instancetype/generate.go`) or loaded from `INSTANCE_TYPES_FILE`. That works for small VMs, but
does not fit large, latency-sensitive workloads:

1. **No type matches a NUMA node.** To get a VM that uses one NUMA node completely, the operator has to know the
   exact usable size of every host (after `reservedcpus` / `reservedmemory`) and hand-write a type per size.
   Hosts with different CPUs need different types.
2. **Nothing guarantees the VM stays inside one NUMA node.** Pinned placement restricts candidate CPUs to NUMA nodes
   with enough free memory and then takes CPUs by topology, which *prefers* packing but may return CPUs from
   several NUMA nodes (`resourcemanager/placement.go: pinned.place`).
3. **Small VMs fragment NUMA nodes.** A `c1.2VCPU-4GB` can land in the middle of an empty NUMA node, so the next
   "whole NUMA node" VM no longer fits anywhere on that host.

## 2. Goals

- Three new instance families, `n1`, `n2` and `n4`, whose sizes are derived at runtime from the discovered host
  NUMA topology. The family digit is the slot fraction: a NUMA node is divided by 1, 2 or 4, CPU and memory together.
- Every NUMA VM fits **strictly** inside one NUMA slot: pinned to the slot's CPUs, memory bound to its NUMA node.
- Exact capacity per slot shape: no "lowest common denominator" sizing across heterogeneous hosts.
- Simple selection from a NodePool by `instance-family`, without matching on generated names.

### Non-goals

- Per-NUMA reservation overrides in the node settings file (reservations are split evenly, §4).
- A price premium or discount for NUMA types. Pricing stays linear (`priceFromResources`).
- Fixing the existing accounting quirk where a regular VM spanning two NUMA nodes is charged its full memory on
  each of them.
- Slot fractions other than 1, 2 and 4.
- Shared placement zones (`simple`, `simple-with-cpu-overcommit`): they have no pinning, so they never offer NUMA
  types.

## 3. Configuration

NUMA types are configured through the existing instance types file (`-instance-types-file` / `INSTANCE_TYPES_FILE`).
Without an instance types file, the predefined list has the `n1` and `n2` templates.
An entry with a `numa` field is a **template**, not an instance type:

```json
[
  {
    "name": "n1",
    "numa": 1,
    "capacity": { "ephemeral-storage": "30Gi", "pods": "110" }
  },
  {
    "name": "n2",
    "numa": 2,
    "capacity": { "ephemeral-storage": "30Gi", "pods": "110" }
  },
  {
    "name": "n4",
    "numa": 4,
    "capacity": { "ephemeral-storage": "30Gi", "pods": "110" }
  },
  {
    "name": "c1.2VCPU-4GB",
    "capacity": { "cpu": "2", "memory": "4Gi", "ephemeral-storage": "30Gi", "pods": "64" }
  }
]
```

- `name`: the family; it becomes the prefix of the generated names and the `instance-family` label. The docs use
  `n1`, `n2`, `n4`, but the name is free-form: what makes an entry a NUMA template is `numa`, not its name.
- `numa`: the slot fraction, `1`, `2` or `4`. The loader rejects any other value.
- `capacity`: `ephemeral-storage` and `pods` are taken from the template. `cpu` and `memory` are ignored; they come
  from the host.
- `overhead`: optional. When omitted, it is computed from the generated capacity with the existing
  `kubeReservedResources` / `systemReservedResources` / `evictionThresholdResources`.

Templates and static entries can be mixed. As today, the file **replaces** the built-in defaults, so a file with
only NUMA templates means only NUMA types exist.

`InstanceTypeStatic` gains one field:

```go
// NUMA marks the entry as a NUMA template and is its slot fraction: 1, 2 or 4.
NUMA int `json:"numa,omitempty"`
```

## 4. NUMA node shape

For every zone using pinned placement (`static` policy), and for every NUMA node on it:

```
cpus(node)   = CPUsInNUMANode(node) - reservedcpus             // reserved IDs reduce the node that holds them
memory(node) = hugepagePool(node)                              // when the zone has a hugepage pool
             | NUMAInfo.MemSize - reservedmemory / numNUMA     // otherwise; the reservation is split evenly
```

`reservedcpus` and `reservedmemory` come from the node settings file (`settings.NodeSettings`). Because reserved
CPU IDs are subtracted from the node they physically belong to, NUMA node 0 is usually smaller than the others
and gets its own slot shapes.

When the zone has a hugepage pool, the node-capacity guest already reports each NUMA node's memory as the pool, and
NUMA VMs are launched with hugepages (§7).

A host with a single NUMA node, or where NUMA is not detected, is treated as one NUMA node covering the whole host.

## 5. NUMA slots

Each NUMA node is cut into aligned **buddy slots**:

```
n1  fraction 1  [ ............................ ]
n2  fraction 2  [ ............. ][ ............. ]
n4  fraction 4  [ ...... ][ ...... ][ ...... ][ ...... ]
```

- The usable CPUs of the node are ordered by uncore cache (CCX), then physical core, then thread.
- A slot of fraction `k` has `floor(cpus / k)` CPUs, rounded down to whole physical cores (an even number when
  SMT is on), and `floor(memory / k)` memory, rounded down to whole GiB.
- Slots are carved contiguously from that order. When the size allows, slot edges snap to CCX boundaries.
- Quarters nest inside halves, and halves nest inside the whole node, so a free half is exactly two free quarters.
- CPUs left over by rounding stay usable by regular instance types, but no NUMA slot covers them.

A slot is **free** when all three hold:

1. none of its CPUs is pinned,
2. its NUMA node still has at least the slot's memory free,
3. the zone still has room for it after CPU share groups: `|usable − pinned| − eCPUs ≥ slot CPUs`
   (see [scheduler-cpushare.md](scheduler-cpushare.md) §6).

The third rule is needed because CPU share groups have no CPU set in Karpenter's books: the scheduler may have put a
group on the slot's CPUs, and the group can only be moved away if the zone has room for it elsewhere.
The same rule also subtracts the vCPUs of virtual machines under shared placement, so every free slot also passes
Reserve's admit check.

## 6. Generated instance types

Each distinct `(family, slot shape)` becomes one Karpenter instance type, named with the existing convention:

```
<family>.<cpu>VCPU-<memory>GB      e.g. n1.30VCPU-126GB, n2.16VCPU-63GB, n4.8VCPU-31GB
```

- **Exact capacity.** Karpenter requires one `Capacity` per type, and `InstanceType.Name` must equal the node's
  `node.kubernetes.io/instance-type` label: core uses it for drift (`InstanceTypeNotFound`), consolidation, cost and
  DRA lookups. Encoding the slot shape in the name keeps both rules true and lets every host advertise its real size.
- **Merging.** Identical slot shapes on different hosts or NUMA nodes produce the same name, so a homogeneous
  cluster gets exactly three types. The fraction is the family, so a half of a big host never merges with a whole
  small host even when their sizes are equal (`n2.16VCPU-63GB` vs `n1.16VCPU-63GB`).
- **Minimum memory.** A slot shape with less than 1GiB of memory per vCPU (memory GiB < vCPUs) gets no type:
  the slot shape is skipped in every NUMA family.
- **Offerings.** Each type has an offering only in the zones that have that slot shape. The offering is available
  when that zone has at least one free slot of that shape (§5).
- **Labels.** Requirements carry the usual `instance-type`, `instance-family`, region, zone and capacity type. No
  new label is added (see [ADR 0002](adr/0002-family-digit-encodes-fraction.md)). NodePools select on the family:

  ```yaml
  requirements:
    - key: karpenter.proxmox.sinextra.dev/instance-family
      operator: In
      values: ["n1"]
  ```

- **Pricing.** Pricing is unchanged: `priceFromResources(capacity)`.

Types are regenerated on every `UpdateInstanceTypeOfferings` from the current capacity view. The static entries
from the file are kept as they are, and the NUMA types are rebuilt.

### 6.1 Topology changes

If a host's slot shapes change (new reservations, hardware change), its NUMA types get new names. A NodeClaim still
labelled with the old name would otherwise be flagged `InstanceTypeNotFound` and replaced, which would roll every
NUMA VM in the zone because of a settings tweak.

To avoid that, a generated type whose slot shape is gone **stays in the list while any live NodeClaim references
it**, with its offerings marked unavailable. Core drift checks only for a *compatible* offering, not an available
one, so those nodes stay and age out normally. Once no NodeClaim references the type, it is dropped. Rolling them
anyway is an explicit operator action.

The same holds per zone: when one host loses a shape that other hosts still have, the type gets an unavailable
offering in the zone of each NodeClaim that uses it there. The NodeClaims are listed on every offerings refresh; a
type that left the generated list takes its slot shape from its name and the rest from its family's NUMA template.
Each kept offering carries the capacity type the NodeClaim is labelled with, so changing a template's capacity type
does not roll its nodes either.

Removing a NUMA template drops its types, kept or not, so their nodes drift: that is the explicit operator action.
If the NodeClaims cannot be listed at startup, the operator exits rather than start without the kept types and let
drift roll the nodes; on a later refresh it keeps the types of the last successful listing and reports the error.

## 7. Launch

When Karpenter launches a NUMA type in a zone:

1. The instance provider recognises the type as generated from a NUMA template and asks the capacity provider for
   a **strict slot allocation**: a free slot of that fraction and shape in the zone.
2. The VM gets the slot's CPUs as its affinity (1:1 pinning, as for any pinned VM) and one guest NUMA node:
   `numa0: cpus=0-<n-1>,hostnodes=<node>,memory=<mem>,policy=bind`. When the zone has a hugepage pool, the VM is
   created with `hugepages` set to the pool's page size.
3. If no slot is free (it was taken between the offering check and the launch), or the placement would span NUMA
   nodes, the launch fails with `InsufficientCapacityError`. Karpenter marks the offering unavailable and tries
   elsewhere. There is no fallback to a non-aligned placement: a NUMA VM that spans NUMA nodes defeats its purpose.

Because each generated type has its exact size, the delivered VM matches what Karpenter planned for, and the
type's `Overhead` is correct as is.

If the slot's CPUs are currently used by a CPU share group, the scheduler moves the group on its next rebalance
(pinned VMs take priority, see [scheduler-cpushare.md](scheduler-cpushare.md) §8.2).

## 8. Pinned placement changes

`pkg/providers/cloudcapacity/resourcemanager` (`zonecapacity.go`, `placement.go`):

- **Per-NUMA reserved memory.** Each NUMA node starts at `MemSize - reservedmemory / numNUMA` (or its hugepage
  pool) instead of the raw node size. Today only the zone total is reduced.
- **Slot view.** New read-only queries for the instance type provider: the slot shapes of every NUMA node, and
  whether a slot of a given shape is free (§5). Both are pure functions of the topology, reservations and usage.
- **Strict slot allocation.** A new reserve path takes a fraction and slot shape, picks a free slot
  (deterministically: lowest NUMA node, then lowest slot index), and reserves exactly its CPUs and memory on that
  node, or returns an error.
- **Soft packing for regular VMs.** When `op.NUMANodes` is not set, candidate NUMA nodes whose whole slot is free
  are tried last; the others are tried first, ordered by what the VM leaves them (fullest first). Within a node,
  CPUs are taken from those covered by the fewest free slots first, so a VM that must break a slot breaks the
  smallest one. A regular VM still falls back to any CPUs, including spanning NUMA nodes, when that is the only
  fit, and soft packing never makes it span more NUMA nodes than it would without it. There is no hard
  partitioning: an `n1` offering is simply unavailable while its node is touched.

Tracking existing VMs needs no new logic. A NUMA VM is observed as a pinned VM whose CPUs happen to cover a slot.

The scheduler applies the same soft packing to CPU share groups: new groups go to the NUMA node with the most
pinned CPUs first, so they rarely sit on whole free slots and rarely have to move.

## 9. Worked example

Host with 2 sockets, 1 NUMA node each, 16 cores / 32 threads and 128 GiB per node, no hugepage pool, settings:

```json
{ "reservedcpus": [0, 32], "reservedmemory": 4294967296 }
```

CPUs 0 and 32 are SMT siblings on NUMA node 0.

| NUMA node | CPUs | Memory | n1 | n2 (×2) | n4 (×4) |
|---|---|---|---|---|---|
| 0 | 32 − 2 = 30 | 128 − 2 = 126 GiB | 30 vCPU / 126 GiB | 14 vCPU / 63 GiB | 6 vCPU / 31 GiB |
| 1 | 32 | 126 GiB | 32 vCPU / 126 GiB | 16 vCPU / 63 GiB | 8 vCPU / 31 GiB |

Generated types:

```
n1.30VCPU-126GB     n2.14VCPU-63GB     n4.6VCPU-31GB     (NUMA node 0)
n1.32VCPU-126GB     n2.16VCPU-63GB     n4.8VCPU-31GB     (NUMA node 1)
```

On node 0, rounding leaves 2 CPUs outside the halves and 6 outside the quarters. Regular VMs can use them, and
soft packing (§8) steers regular VMs there first.

A second host with the same CPU model and settings produces the same six names, so its zone simply adds offerings
to the existing types.

## 10. Edge cases

- **NUMA node too small for a fraction.** If a quarter would round down to 0 cores, that fraction is not generated
  for the node.
- **Memory-poor NUMA node.** Slot CPUs can be free while the node's memory is consumed by other VMs. The slot is
  then not free (§5), and the offering is unavailable.
- **CPU share groups fill the zone.** Slot CPUs are unpinned and the memory is there, but `eCPUs` leave no room to
  move the groups away. The slot is not free (§5, rule 3).
- **Asymmetric CCX layout.** When slot edges cannot snap to CCX boundaries, slots are still carved contiguously in
  CCX order. Alignment is best effort; strict NUMA containment is not.
- **Zone switches CPU policy.** If a zone moves from `static` to `simple`, its offerings disappear and existing NUMA
  VMs are handled as in §6.1.
- **VMs created outside Karpenter.** They are tracked by the existing capacity sync. If they touch a slot, that
  slot is not free.

## 11. Implementation plan

1. `InstanceTypeStatic.NUMA` field (integer fraction). The file loader keeps NUMA templates aside from static
   types and rejects fractions other than 1, 2 and 4.
2. Pinned placement: per-NUMA reserved memory (or hugepage pool), slot computation, slot-free query including the
   CPU share group count, strict slot allocation. Unit tests on synthetic topologies, including the worked example
   (§9).
3. Capacity provider: expose per-zone slot shapes and availability for `static` zones.
4. Instance type provider: generate `<family>.<cpu>VCPU-<mem>GB` types and offerings on every offerings refresh,
   and keep the NUMA types live NodeClaims still use (kept NUMA types) (§6.1).
5. Instance provider: strict slot allocation on launch, `InsufficientCapacityError` on failure, guest NUMA config,
   hugepages when the zone has a pool.
6. Pinned placement: soft packing for regular VMs.
7. Documentation: `docs/instancetypes.md` (templates, naming, NodePool example) and `docs/noderesource.md`
   (per-NUMA reservations).
