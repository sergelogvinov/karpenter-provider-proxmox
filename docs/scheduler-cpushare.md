# CPU Share Instance Types Design

Design notes for new instance type families whose VMs share a dedicated set of host CPUs: two, three or four VMs
run on the same CPUs, each with its own dedicated memory.

Status: proposed.

## 1. Problem

Every instance type today gives a VM either pinned CPUs of its own (`static` policy) or a share of all the
unpinned CPUs of the host (`simple` policy). There is nothing in between:

1. **Small, mostly idle nodes are expensive.** A node that needs 2 vCPUs to absorb bursts but averages 20% CPU
   still costs 2 whole host CPUs under `static`.
2. **`simple` gives no isolation.** Unpinned VMs float over the whole shared pool (or a slice of it planned by
   `cpumanager.PlanShared`, see [scheduler-shared.md](scheduler-shared.md)), so a VM shares CPUs with an unknown
   and changing set of neighbours.
3. **`simple-with-cpu-overcommit` is host-wide.** The ratio applies to every VM in the cluster; it cannot be chosen
   per workload.

What is missing is a type that is cheap like overcommit but has bounded, known sharing: "this VM shares its CPUs
with at most N−1 other VMs of the same shape".

## 2. Goals

- Three new instance families: `e2`, `e3`, `e4`. A VM of family `eN` shares its CPUs with up to N−1 other VMs.
- Memory is never shared: each VM has its own memory, as for any other type.
- The guest sees the full vCPU count and may burst to it when its neighbours are idle.
- Karpenter only counts usage; the [Proxmox Scheduler](scheduler.md) decides at runtime which VMs share which CPUs.
- Supported with the `static` and `simple` node policies.
- The built-in list has the `e2` family; `e3` and `e4` appear only when the operator configures them.

### Non-goals

- Support for `simple-with-cpu-overcommit`. That policy already makes every VM share CPUs through its ratio, so
  `e` types would only add a second, conflicting accounting rule. They are not offered there.
- CPU bandwidth control (`cpulimit`, cgroup quotas). Sharing is fair only in the sense of the Linux scheduler on
  a confined cpuset.
- Mixed groups (different fractions or sizes sharing the same CPUs).
- Per-NUMA accounting of CPU share VMs in Karpenter (§6).

## 3. Model

A **CPU share group** is a set of `vCPU` host CPUs with `N` seats. Every member of a group has the same family and
the same vCPU count, and all of their vCPU threads may run on any CPU of the group.

```
e2.2VCPU-4GB, 2 VMs:

  VM 301  [vCPU0 vCPU1]  4 GiB ─┐
                                ├─► host CPUs 24,56   (one physical core with its SMT sibling)
  VM 302  [vCPU0 vCPU1]  4 GiB ─┘
```

- Each member sees `vCPU` CPUs and is guaranteed `vCPU/N` of them on average.
- A group with free seats still takes `vCPU` CPUs; its members get the spare time.
- Memory is not part of the group: each VM has its own, accounted as usual.

### 3.1 Families and sizes

| Family | Seats (N) | Guaranteed share |
|---|---|---|
| `e2` | 2 | 1/2 |
| `e3` | 3 | 1/3 |
| `e4` | 4 | 1/4 |

Sizes: vCPU in `{2, 4, 8}`, always even so that a group covers whole physical cores, with memory ratios 1:2 and 1:4.
Names follow the existing convention `<family>.<vCPU>VCPU-<memory>GB`, e.g. `e2.2VCPU-4GB`, `e3.4VCPU-16GB`,
`e4.8VCPU-16GB`.

The letter `e` belongs to the CPU share families only. The generator (`pkg/providers/instancetype/generate.go`) rejects
a memory ratio without a dedicated family (`c`, `t`, `s`, `m`, `x` for 2, 3, 4, 8, 16) instead of naming it `e1.*`.

## 4. Configuration

The built-in list generated by `DefaultProvider` has the `e2` family, of the same sizes as the dedicated families.
The `e3` and `e4` families are opt-in through the instance types file (`-instance-types-file` / `INSTANCE_TYPES_FILE`).

`InstanceTypeStatic` gains one field:

```go
// CPUShare is the number of VMs that share the instance's CPUs: 2, 3 or 4. Zero means dedicated CPUs.
CPUShare int `json:"cpushare,omitempty"`
```

```json
[
  {
    "name": "e2.2VCPU-4GB",
    "cpushare": 2,
    "capacity": { "cpu": "2", "memory": "4Gi", "ephemeral-storage": "30Gi", "pods": "64" }
  },
  {
    "name": "e4.8VCPU-32GB",
    "cpushare": 4,
    "capacity": { "cpu": "8", "memory": "32Gi", "ephemeral-storage": "30Gi", "pods": "110" }
  }
]
```

- `cpushare` is what makes a type a CPU share type, not its name. The family can be called anything.
- `capacity.cpu` is the full vCPU count the guest sees.
- The loader rejects `cpushare` values other than 0, 2, 3 and 4.

`cmd/instancetypes` gets a `--cpushare` flag (comma-separated, e.g. `2,3,4`). For each value it generates the
`e<N>` family for the requested CPUs and memory factors, with `cpushare` set.

NodePools select the families with the existing `LabelInstanceFamily` label (`pkg/apis/v1alpha1/labels.go`); no
new label is added (see [ADR 0002](adr/0002-family-digit-encodes-fraction.md)):

```yaml
requirements:
  - key: karpenter.proxmox.sinextra.dev/instance-family
    operator: In
    values: ["e2"]
```

## 5. Capacity and pricing

- **Capacity.** The instance type's `cpu` capacity is the full vCPU count, and the kubelet reports the same. The
  type is burstable: Kubernetes may place up to `vCPU` cores of requests on a node that is only guaranteed
  `vCPU/N`. Operators choose `e` types for workloads where that is acceptable.
- **Overhead.** Computed from the capacity as for any type (`kubeReservedResources` and friends).
- **Pricing.** `priceFromResources` is called with `cpu = vCPU/N` and the full memory, so an `e2.2VCPU-4GB` costs
  as much CPU as a 1 vCPU type. This is what makes Karpenter prefer `e` types for NodePools that allow them: a
  NodePool that needs dedicated CPUs excludes the `e` families with a `NotIn` requirement (§4).

## 6. Karpenter accounting

Karpenter never assigns CPUs to a CPU share VM. It only counts how many host CPUs the CPU share groups of a zone need.

For each size class `(N, vCPU)` with `count` VMs in the zone:

```
groups(N, vCPU) = ceil(count / N)
eCPUs           = Σ groups(N, vCPU) × vCPU
```

So a lone `e2.2VCPU` VM costs 2 CPUs, and a second one in the same zone costs nothing more: it fills the open
seat. Sharing is never assumed across classes.

`resourcemanager.ZoneCapacity` gets a third kind of record next to pinned and shared placement: a CPU share record holds
`(N, vCPU)` and its memory. `usage()` adds `eCPUs` computed as above.

- **`static` policy.** `eCPUs` are subtracted from the CPUs a pinned VM can be placed on, as a count:
  a new pinned VM fits only if `|usable − pinned| − eCPUs ≥ cpus`. Its CPUs are still picked by `pinned.place`
  from `usable − pinned`, so it may land on CPUs an `e` group currently uses; the scheduler moves the group
  (§8.3).
- **`simple` policy.** `eCPUs` are subtracted from `sharedCapacity` before unpinned VMs are counted against it.
- **`simple-with-cpu-overcommit` policy.** `e` types get no offerings.
- **NUMA slots.** A NUMA slot ([scheduler-numa.md](scheduler-numa.md) §5) is free only
  if the zone still has room after `eCPUs`, because launching a NUMA VM may push a CPU share group off the slot's
  CPUs.
- **Fit.** An `e` offering is available in a zone when adding one VM of that class keeps the zone's CPUs and memory
  within capacity. Because of the `ceil`, a zone with an open seat of that class always fits on CPU.
- **Memory.** Charged at the zone level only. CPU share VMs get no `numaN: hostnodes=…` binding and no per-NUMA memory
  record.

## 7. Launch and resync

When Karpenter launches an `e` type:

1. The capacity provider reserves a CPU share record for the zone (no CPU set).
2. The VM is created with `cores = vCPU`, no `affinity`, no NUMA binding, and the description token
   `cpushare=<N>`:

   ```
   Karpenter managed instance, class=default, capacity-type=on-demand, cpushare=2
   ```

On resync, zone capacity (`pkg/zonecapacity`) parses `cpushare=<N>` from the description, so VMs created by hand
with the token are accounted the same way. A VM with both `affinity` and `cpushare` is treated as pinned and the token is ignored, with a warning.

A VM resized in place, or whose `cpushare` changes, simply moves to another size class on the next resync.

## 8. Scheduler

### 8.1 VM class

`classifyVM` (`cmd/proxmox-scheduler/scheduler.go`) gets a new class:

| Class | Detection | Handling |
|---|---|---|
| `cpushare` | no `affinity`, `cpushare=<N>` in the description | Member of a CPU share group; all threads masked to the group's cpuset. |

`cpushare` VMs are confined whatever `--shared-policy` says, and floating VMs are always kept off the groups'
CPUs. With `none`, floating VMs are masked to the whole `sharedPool` (§8.2) instead of being left on all CPUs; with
`partition`, they are planned on it by `PlanShared` as today.

### 8.2 Pools and priority

```
exclusivePool = ∪ affinity of pinned + constrained VMs
groupPool     = allCPUs − reservedCPUs − exclusivePool
sharedPool    = groupPool − ∪ group cpusets
```

Priority: pinned > `cpushare` groups > floating. Groups keep their full width; only floating VMs absorb
oversubscription (`PlanShared` oversubscribed mode). If even the groups do not fit in `groupPool` (e.g. a VM created
by hand), the groups that do not fit are masked to the remaining `groupPool` and the scheduler logs it, instead of
failing (§8.3, step 5).

### 8.3 Group planner

A pure function next to `PlanShared`:

```go
// pkg/zonecapacity/internal/cpumanager/planner_cpushare.go
type CPUShareRequest struct {
    VMID    int
    CPUs    int           // cores from the VM config
    Share   int           // N from the cpushare token
    Current cpuset.CPUSet // currently applied set, for stability
}

type CPUShareGroup struct {
    CPUs    cpuset.CPUSet // every member is masked to it; empty: not seated, left as is
    Members []int         // VMIDs, in order
}

// pinned orders the NUMA nodes for new groups; the notes are the spills and groups that did not fit.
func PlanCPUShare(logger logr.Logger, topo *topology.CPUTopology,
    pool, pinned cpuset.CPUSet, reqs []CPUShareRequest) ([]CPUShareGroup, []string, error)
```

`Zone.Plan` calls it on the unpinned CPUs, returns the groups' CPUs in `Plan.Groups` and the ungrouped CPUs
(`sharedPool`) in `Plan.Ungrouped`, and turns the notes into `Plan.Notes`. It adds a drift note when the CPUs the
groups use differ from what `static` accounting charges for them (§6); the scheduler is built for the `static`
node policy.

1. **Classes.** Requests are grouped by `(Share, CPUs)`. Each class needs `ceil(count / Share)` groups, the same
   number Karpenter counts (§6).
2. **Keep.** Existing groups (members whose `Current` sets are equal) are kept while their cpuset is still inside
   `pool` and disjoint from the other kept groups. Kept groups are filled first, fullest first.
3. **Merge.** When a class has more groups than it needs, the emptiest groups (ties: highest CPU IDs) are dissolved and their members move
   to open seats of the kept ones. Repacking is eager, on every debounced rebalance, so the host's real usage
   matches Karpenter's count. Moving a member is only an affinity change.
4. **Place.** New groups go to the NUMA node with the most pinned CPUs first, so they rarely sit on whole free
   NUMA slots and rarely have to move when a NUMA VM launches. Within that order they take `CPUs` CPUs from the remaining pool with `takeByTopologyNUMAPacked`
   (`CPUSortingStrategyPacked`, whole physical cores with their siblings, aligned by uncore cache). Ties go to the
   lowest node, and a node with no whole cores left is skipped. A group prefers a single NUMA node and keeps it once
   placed; when no node has room it spills across nodes, still on whole cores, and the planner notes the spill. A
   group with an odd width takes any CPUs; an even-width group never falls back to half cores.
5. **Do not fit.** A group with no room left (no whole cores for an even width) is masked to what the other groups
   left of `pool`, up to its width, after every group that fits is placed, so it never overlaps another group. When
   nothing is left its members are not seated and stay as they are; the note says so.

Determinism: classes are processed by `(CPUs desc, Share asc)`, members by VMID, so the same input always yields
the same plan.

### 8.4 Applying a plan

Each member's vCPU threads and the QEMU process itself (`SetThreadsAffinity` + `SetProcessAffinity`) are masked to
the group's cpuset, as for floating VMs in [scheduler-shared.md](scheduler-shared.md) §5. Applying is idempotent.

The busy CPU governor is applied to every group cpuset. IRQs of passthrough devices are steered to the group cpuset.

### 8.5 Control flow

`cpushare` VMs go through the existing debounced rebalance. A rebalance now runs `PlanCPUShare` first, then
`PlanShared` on the `sharedPool` it leaves.

## 9. Worked example

The 64-CPU / 4-NUMA host from [scheduler.md](scheduler.md) (`0-7,32-39` = node 0, siblings included), with
`reservedCPUs = 0,32`:

```
VM 100  cores=8  affinity=8-15              → pinned,   exclusive 8-15
VM 301  cores=2  cpushare=2                 → e2.2VCPU
VM 302  cores=2  cpushare=2                 → e2.2VCPU
VM 303  cores=2  cpushare=2                 → e2.2VCPU
VM 401  cores=8  cpushare=4                 → e4.8VCPU
VM 200  cores=4  (no affinity)              → floating

class (2, 2): 3 VMs → 2 groups → 4 CPUs
class (4, 8): 1 VM  → 1 group  → 8 CPUs
eCPUs = 12   (Karpenter counts the same)

group A (301, 302) → 16,48
group B (303)      → 17,49       one free seat
group C (401)      → 18-21,50-53 three free seats

sharedPool = 1-7,22-31,33-47,54-63   (40-47 are the siblings of VM 100's CPUs)
VM 200     → its partition of sharedPool (partition) or all of sharedPool (none)
```

The groups above are as already applied, which the planner keeps. Planned from scratch, they go to node 0 instead:
node 1 has the most pinned CPUs but no whole core left, and node 0 is the lowest of the rest.

VM 302 stops: class `(2, 2)` now has 2 VMs and needs 1 group. Groups A and B have one member each; the tie goes
to the group with the lower CPU IDs, so B is dissolved: VM 303 moves to 16,48 and 17,49 returns to the shared pool.

A new `e2.2VCPU` VM in this zone is free on CPU for Karpenter as long as a seat is open.

## 10. Edge cases

- **Odd core count.** A VM created by hand with `cpushare` and an odd `cores` is allowed; its group is `cores` CPUs
  wide and may share a physical core with something else.
- **`cpushare` VM in a `simple-with-cpu-overcommit` cluster.** Created by hand only. Karpenter accounts it as a
  regular unpinned VM; the scheduler, built for `static`, still groups it and does not report the difference (§8.3).
- **Pinned VM lands on a group.** In a `static` cluster Karpenter may pick CPUs a group holds (§6). The group is no
  longer inside `groupPool` and the next rebalance moves it.
- **Fragmented NUMA nodes.** Karpenter counts at host level, so a group can be "free" in total but have no single
  NUMA node with room. It spills (§8.3).
- **Daemon restart.** No persisted state: groups are rebuilt from the members' current masks (members with equal
  masks form a group) and the planner converges.
- **VM stop during a rebalance.** As in [scheduler-shared.md](scheduler-shared.md) §12: `ESRCH` drops the VM, the
  next tick re-plans.

## 11. Implementation plan

1. Accounting: `VMResources.CPUShare`, `cpushare=` parsing in `GetResourceFromVMConfig`, the CPU share record in
   `ZoneCapacity` with the `ceil` count, and its effect on `static` and `simple` fit. Table tests per policy,
   including the worked example (§9).
2. Instance types: `InstanceTypeStatic.CPUShare`, loader validation, pricing with `vCPU/N`, no offerings under
   `simple-with-cpu-overcommit`, and `cmd/instancetypes --cpushare`.
3. Launch: `cpushare=<N>` description token, no affinity and no NUMA binding for `e` types.
4. Scheduler: `cpushare` class in `classifyVM`, `cpumanager.PlanCPUShare` with table tests (keep, merge, spill,
   determinism), wiring into the rebalance before `PlanShared`, independent of `--shared-policy`.
5. Documentation: `docs/instancetypes.md` (families, file field, NodePool example), `docs/scheduler.md` (new class),
   `docs/noderesource.md` (accounting).
