# Without root, the scheduler pins and the template carries hugepages

Proxmox lets only `root@pam` set some VM options; the controller writes two of them on launch, `affinity` and `hugepages`. The controller decides per region whether it is privileged: logging in as `root@pam` is root, any API token or other user is not. As root nothing changes. Without root the controller never writes `affinity` or `hugepages`: a pinned VM's host CPUs travel only in the `affinity=` description token, and the proxmox-scheduler, which already reads that token, pins the VM's threads at runtime. Hugepages come from the template the VM is cloned from. The controller still writes `numaN` with `hostnodes` and `policy=bind`, which needs no root, so a strict slot allocation still binds the VM's memory to its NUMA node and one template per page size serves every NUMA node.

A NUMA NodePool therefore uses its own NodeClass whose template, a `ProxmoxUnmanagedTemplate`, has `hugepages` set. Without root, `GetInstanceTypes` checks the NodeClass's template against each zone and drops what it cannot launch correctly, setting a status condition on the NodeClass: in a zone with a hugepage pool, NUMA types need a template whose `hugepages` matches the pool's page size, and non-NUMA types need a template without `hugepages`. A VM template with `affinity` set is unusable for every type, so the `ProxmoxUnmanagedTemplate` drops it from its template placements instead (see Consequences). As root the controller sets or clears these options itself, so no check applies.

## Considered Options

- Detect privilege by trying to set `affinity` and falling back on a permission error: rejected, every failed attempt leaves a half-configured VM to roll back, and the answer is known from the credentials at startup.
- The scheduler writes `affinity` and `hugepages` as root before the VM starts: rejected, it turns a host daemon into a config writer, and the controller would have to create the VM stopped and wait for it; the scheduler stays passive and only applies the description token.
- The controller waits for the scheduler to pin a VM before reporting the launch: rejected, a few seconds unpinned during boot is harmless.
- Give every VM in a hugepage zone hugepages, so one template serves all types: rejected, regular VMs would draw from the hugepage pool, which zone capacity does not track for them. Except in a zone whose pool spans one NUMA node: zone capacity charges every VM to the zone budget, which is the pool, and caps each node's free memory by the zone's, so with one node the two budgets are the same and a regular VM drawing from the pool keeps the accounting exact. There a hugepage template also offers non-NUMA types, which launch with `numa: 1` and one `numa0` holding all their vCPUs and memory, bound (`hostnodes`, `policy=bind`) to the zone's NUMA node, replacing the template's `numaN`, since Proxmox needs `numa` for `hugepages` and its default per-socket split wants a host node per socket. With two or more nodes a regular VM's pages land on node 0 unseen by the per-node view, and a NUMA slot later fails to start, so the split stays.
- One template per host NUMA node: not needed while `numaN` `hostnodes` stays settable without root.
- A `hugepages` field on the managed `ProxmoxTemplate`: deferred, a non-root controller could not create such a template either; it can be added later without breaking anything.
- Launch NUMA types without hugepages when the template has none, or fail at Create: rejected, the first breaks slot memory accounting (a slot's memory is the pool), the second loops through launch, failure and backoff.

## Consequences

Without root, the proxmox-scheduler is required for pinned placement: the `affinity` option on a VM is no longer the source of truth, the description token is, and nothing pins a VM on a host where the scheduler is not running. The controller logs a warning for a pinned zone without a node-capacity guest, but cannot prove the scheduler is alive.

The template becomes part of the placement contract: a NodeClass is valid only for the instance types its template fits, so operators keep separate NodeClasses for NUMA and non-NUMA NodePools in hugepage zones of two or more NUMA nodes; in one of one NUMA node a single hugepage NodeClass serves both. The template records the `hugepages` and `affinity` its VM templates share in `status.template`, and a `ProxmoxVirtualMachineTemplateConsistent` condition on the template, not the NodeClass and not part of Ready, turns false when its VM templates disagree. A template whose `status.template` is unset, because its VM templates disagree or are not known yet, offers nothing in hugepage zones, since a clone's `hugepages` cannot be predicted; `hugepages: any` is not a page size, so it matches no pool and offers nothing there either. The drops are reported by a `TemplateCompatible` condition on the NodeClass, not part of Ready, which is false only for a problem of the template (a page size that does not match the pool, a template whose hugepages is not known, or a zone where the NodeClass offers nothing) and stays true, naming what is dropped, on a NodeClass meant only for NUMA or only for non-NUMA types.

Without root, the `ProxmoxUnmanagedTemplate` drops VM templates with `affinity` set from its template placements, since every clone would inherit CPUs the controller can neither replace nor clear; NodeClasses using it lose those zones.

Two Proxmox behaviours this rests on were verified (#294): only `root@pam` itself may set `affinity`, `hugepages`, `keephugepages` and `args`, and an API token of `root@pam` does not pass that check; `numaN`, `hostnodes` included, needs no root. The controller writes neither `keephugepages` nor `args`. If a PVE release changes either behaviour, this decision is reopened: root tokens passing would make privilege "the user is `root@pam`, with or without a token", and `hostnodes` needing root would need one template per NUMA node.

"Hugepage template" here is a Proxmox VM template; it is unrelated to the **NUMA template**, an instance types file entry.
